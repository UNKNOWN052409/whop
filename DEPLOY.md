# DEPLOY.md — operator runbook

How to take this store from this repository to a live URL on Vercel, and how to
prove it actually works before you tell anyone it does.

Read this end to end the first time. Every step that can be done in the wrong
order is marked **⚠ ORDER MATTERS**.

---

## 0. What is verified, and what is not

Be clear-eyed about this before you rely on anything below.

**Verified at the time this document was written (in this repository):**

| Check | Result |
|---|---|
| `pnpm typecheck` (`tsc --noEmit`, strict + `noUncheckedIndexedAccess`) | 0 errors |
| `pnpm build` | passes |
| `pnpm test` | 144 / 144 passing |
| Database-backed suites (concurrency, end-to-end) | **SKIPPED** — they need `TEST_DATABASE_URL`. A green run locally does **not** mean the oversell protection has been exercised. |

**Not verified.** Nothing in this runbook has been executed against a live Vercel
project, a live Whop account, or a live Postgres. The steps are written from the
code in this repository plus Vercel's and Whop's documented behaviour. Treat
§7's verification checklist — not this document — as the evidence that the
deployment works.

**Two known gaps in the repository itself.** Both are called out again where they
bite, and neither is fixed by this runbook:

1. **There is no `prisma/migrations/` directory.** `pnpm db:deploy`
   (`prisma migrate deploy`) will therefore be a **silent no-op**: with no
   migration folder it applies nothing and exits 0. See §4.
2. **There is no admin UI page for MFA enrolment.** The seed tells you to enrol
   at `/admin/account`, but that page does not exist. Enrolment is only reachable
   through `POST /api/auth/mfa/enrol`. §8 gives you a working sequence.

## 1. Prerequisites and accounts

You need all six. Do not start until each row is real — half of them cannot be
provisioned in five minutes.

| # | Account | Why it is needed | Free tier enough? |
|---|---|---|---|
| 1 | **Vercel** | Hosts the app and runs the three crons. | **No — see the plan warning below.** |
| 2 | **PostgreSQL 14+** | Orders, inventory, events, audit trail. Neon, Supabase, Vercel Postgres or your own. | Yes, but read §9 on pooling before you pick one. |
| 3 | **Whop** | The payment provider. Create a **sandbox** company first; only move to a live company at §8. | Sandbox is free. |
| 4 | **Upstash Redis** | Rate limiting, idempotency, queue gauges. Without it rate limiting degrades to per-instance memory. | Yes. |
| 5 | **Inngest** | The durable fulfillment queue. Vercel has no long-lived workers; without Inngest, fulfillment does not run at all. | Yes, for low volume. |
| 6 | **An email provider** | Delivers the redeem code. Amazon SES, Resend, or any SMTP relay. | Resend has a small free tier; SES is effectively free for low volume but needs a verified domain. |

### ⚠ Vercel plan: Hobby will not run this configuration

Two things in `vercel.json` exceed the Hobby plan's limits:

- **Function duration.** Reconciliation declares `maxDuration: 300`. Hobby caps
  function duration well below that, and will reject or silently clamp the
  setting.
- **Cron frequency.** `/api/cron/fulfillment-recovery` runs every 5 minutes.
  Hobby limits cron jobs to a daily schedule.

On Hobby, the 5-minute recovery sweep silently never fires — and that sweep is
the mechanism that recovers a paid order whose worker died. You would lose paid
orders during an incident with no error message anywhere.

**Use a paid Vercel plan.** Confirm the exact current limits at
<https://vercel.com/docs/limits> before you buy; they change.

## 2. Generate the secrets locally

Four secrets are generated by you. None of them come from a vendor. Run these on
your own machine — **not** on the server, and do not paste them into a chat, a
ticket or a commit.

```bash
# AES-256-GCM key over redeem-code inventory. Exactly 32 bytes, base64.
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

# HMAC key for deterministic fingerprints. MUST be a different value.
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

# Session cookie signing key.
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# Cron authorization bearer token. Unique per environment.
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"

# Prometheus scrape token for /api/metrics.
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

Equivalent openssl one-liners, if you prefer:

```bash
openssl rand -base64 32      # ENCRYPTION_KEY
openssl rand -base64 32      # FINGERPRINT_KEY
openssl rand -base64 48      # SESSION_SECRET  (base64 of 48 bytes)
openssl rand -hex 32         # CRON_SECRET / METRICS_TOKEN
```

> ### ⚠ `ENCRYPTION_KEY` IS IRREVERSIBLE
>
> It encrypts every redeem code in your inventory with AES-256-GCM. Lose it and
> **every code you have ever imported is permanently unreadable**. There is no
> recovery path, no key escrow and no reset. Put it in a password manager the
> moment you generate it, and generate a *different* `FINGERPRINT_KEY` — the two
> have different jobs and should not share a key.

Store these in your password manager now, before continuing. You will need
`ENCRYPTION_KEY` again at §4 to run the seed.

## 3. Environment variables in Vercel

Push the repository and let Vercel create the project:

```bash
vercel            # first time: creates the project, links it, deploys a preview
```

Then **Settings → Environment Variables**. Tick which scope each variable applies
to. The table says which.

### 3a. REQUIRED — the app will not boot in production without these

`src/lib/env.ts` calls `assertProductionConfig()` from `src/instrumentation.ts`,
which **throws at boot** if any of these are missing. The deploy will look
successful in the Vercel dashboard and then every request will 500. This is
deliberate — a payment platform must not boot half-configured — but it means you
must set them **before** the first production deploy, not after.

| Variable | Scope | Value / where to get it |
|---|---|---|
| `DATABASE_URL` | Production | Pooled Postgres URL + `sslmode=require`. See §3c and §9. |
| `ENCRYPTION_KEY` | Production | §2. Base64, 32 bytes. |
| `FINGERPRINT_KEY` | Production | §2. A **different** random value. |
| `SESSION_SECRET` | Production | §2. Base64, 48 bytes. |
| `NEXT_PUBLIC_APP_URL` | Production | `https://yourdomain.com` — no trailing slash. |
| `WHOP_API_KEY` | Production | Whop dashboard → Developers. Needs all five scopes below. |
| `WHOP_ACCOUNT_ID` | Production | Whop dashboard → Settings → `biz_…` |
| `WHOP_WEBHOOK_SECRET` | Production | Shown **once** when you create the webhook. §5. |
| `WHOP_ENVIRONMENT` | Production | `sandbox` for §7. Flip to `production` at §8. |
| `UPSTASH_REDIS_REST_URL` | Production | <https://console.upstash.com> |
| `UPSTASH_REDIS_REST_TOKEN` | Production | Same page. |
| `INNGEST_EVENT_KEY` | Production | <https://app.inngest.com> → your app. §6. |
| `INNGEST_SIGNING_KEY` | Production | Same page. |
| `EMAIL_PROVIDER` | Production | `SES` \| `RESEND` \| `SMTP` — must match the credentials you supply. |
| Email credentials | Production | `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` **or** `RESEND_API_KEY` **or** `SMTP_*`. |
| `EMAIL_FROM` / `EMAIL_FROM_NAME` | Production | A domain you control and have verified with the provider. |

Whop API key scopes — all five, or checkout creation and verification fail:

```
checkout_configuration:create      create checkout links
checkout_configuration:basic:read   read checkout metadata
payment:basic:read                 verify payments, reconcile
member:email:read                  read buyer email during reconciliation
webhook_receive:payments           receive webhooks
```

### 3b. REQUIRED FOR THE BACKGROUND WORKERS

Not required to boot, required for the store to be correct.

| Variable | What breaks without it |
|---|---|
| `CRON_SECRET` | All three `/api/cron/*` routes return **404**. Reconciliation never runs; expired inventory reservations are never released; stalled fulfillments are never recovered. It is the single most important variable after `ENCRYPTION_KEY`. |
| `ADMIN_BOOTSTRAP_EMAIL` / `ADMIN_BOOTSTRAP_PASSWORD` | Needed **only** while running the seed at §4. Delete both from Vercel afterwards — the seed is a one-shot, and a live admin password in your Vercel env is a standing risk. |

### 3c. OPTIONAL — safe to leave unset, each has a documented default

| Variable | Effect if unset |
|---|---|
| `METRICS_TOKEN` | `GET /api/metrics` returns **404**. That is the intended design — no token means the endpoint does not exist, not that it is open. |
| `LOG_LEVEL` | `info` in production. Use `debug` only while diagnosing; it will log a great deal. |
| `ENABLED_PAYMENT_METHODS` | No method list. Defaults to `CARD` only. Whop's hosted checkout settles cards; `UPI`, `WALLET` and `NETBANKING` are declared unsupported by the provider and are **not** faked. |
| `WEBHOOK_TOLERANCE_SECONDS` | `300`. Whop's own replay window is 300s. |
| `RECONCILIATION_LOOKBACK_HOURS` | `72`. |
| `WHOP_API_VERSION_DATE` | `2026-10-07-2`. **Do not remove this default.** Unpinned requests silently fall back to the `2025-01-01` shapes where the account field is `company_id`, and your orders stop correlating. |
| `DEFAULT_MIN_DISCOUNT_BPS` / `DEFAULT_MIN_MARGIN_BPS` | `500` / `0`, applied only when no `PricingRule` row exists. |
| `MFA_ISSUER` | `Redeem Store` — the issuer label shown in authenticator apps. |
| `CATALOG_CACHE_TTL_SECONDS` | Provider default. |
| `WHOP_DISPUTE_FEE_CURRENCY` | `USD`. |
| `ALERT_CURRENCY` | `usd`. |
| `INNGEST_BASE_URL` | Leave unset. **Setting this on Vercel points the queue at localhost** and fulfillment stops silently. |
| `SUPPLIER_AUTHORIZATION_REF` | Written onto the supplier record by the seed. |

> **Never set `TEST_DATABASE_URL` on Vercel.** The test helpers *replace*
> `DATABASE_URL` with it, so a green `pnpm test` against a Vercel build would
> truncate and rewrite your production orders.

### ⚠ Preview deployments

If you let Vercel build preview deployments with Production-scoped variables,
every preview runs **your crons, against your production database**. Give Preview
its own database and its own `CRON_SECRET`, or disable crons on non-production
branches. Vercel only *fires* crons for production, but a preview can still be
hit manually with the production bearer token if the secrets are shared.

### 3d. `DATABASE_URL` — read this before you paste one

The full pooling explanation is in `.env.example`. The short version:

- **`sslmode=require` is mandatory in production.** A remote Postgres refuses
  plaintext auth, so an unencrypted URL fails on the first deployed query even
  when the identical URL works from your laptop.
- **Use a pooled endpoint.** Neon → the `-pooled` hostname. Supabase → the
  "Connection pooler" host, not `db.<ref>.supabase.co`. Vercel Postgres → the URL
  it hands you **already pools**; leave it alone.
- **Keep `connection_limit` small** (1–5) and set `pool_timeout` (10–30s).

A reasonable starting value:

```
postgres://USER:PASSWORD@HOST:5432/DB?sslmode=require&connection_limit=5&pool_timeout=15&connect_timeout=10
```

## 4. Database: schema, then seed

Run both **from your own machine**, not from Vercel. They need `DATABASE_URL`
pointing at the production database, and the real `ENCRYPTION_KEY`.

```bash
# in the repo root
export DATABASE_URL="postgres://...?sslmode=require&connection_limit=5&pool_timeout=15"
export ENCRYPTION_KEY="<the base64 value from §2>"
```

PowerShell equivalent, if that is your shell:

```powershell
$env:DATABASE_URL   = "postgres://...?sslmode=require&connection_limit=5&pool_timeout=15"
$env:ENCRYPTION_KEY = "<the base64 value from §2>"
```

Note that `export` in PowerShell is an alias for a *different* cmdlet and does not
set environment variables — use `$env:NAME = "value"`.

### 4a. Create the schema

**⚠ ORDER MATTERS — and there is a trap here.**

This repository has **no `prisma/migrations/` directory**. That means
`pnpm db:deploy` (`prisma migrate deploy`) applies nothing and exits successfully
without creating a single table. If you follow the obvious runbook here, you will
get a green command and an empty database, and you will not find out until the
first request.

Pick one:

**Option A — generate a real initial migration (recommended).** Do this on a
branch and commit `prisma/migrations/` so every future environment, including
CI, converges the same way:

```bash
pnpm db:generate
pnpm db:migrate --name init      # creates prisma/migrations/<ts>_init/
git add prisma/migrations && git commit -m "chore: initial Prisma migration"
pnpm db:deploy                   # now this actually applies the schema
```

**Option B — one-time bootstrap, no migration history:**

```bash
pnpm db:push                     # creates the schema directly, no migration files
```

`db:push` is fine for a first production bootstrap and for a dev database. It is
not fine as a long-term strategy: there is no ordered migration history, so every
future schema change is another `push` and you lose the ability to reason about
what is deployed where.

After either option, confirm the tables exist. The quickest check is the studio,
which needs no quoting gymnastics:

```bash
pnpm db:studio
```

Or, if you want a scriptable assertion, a raw query — note that the bash
here-string `<<<` does **not** work in PowerShell or cmd, so pick the form that
matches your shell:

```bash
# bash / Git Bash / WSL
echo 'SELECT count(*) FROM "Product";' | pnpm exec prisma db execute --stdin --schema prisma/schema.prisma

# PowerShell
'SELECT count(*) FROM "Product";' | pnpm exec prisma db execute --stdin --schema prisma/schema.prisma

# cmd.exe
echo SELECT count(*) FROM "Product"; | pnpm exec prisma db execute --stdin --schema prisma/schema.prisma
```

### 4b. Run the seed

```bash
export ADMIN_BOOTSTRAP_EMAIL="owner@yourdomain.com"
export ADMIN_BOOTSTRAP_PASSWORD="<a long unique password>"

pnpm db:seed
```

```powershell
$env:ADMIN_BOOTSTRAP_EMAIL    = "owner@yourdomain.com"
$env:ADMIN_BOOTSTRAP_PASSWORD = "<a long unique password>"
pnpm db:seed
```

The seed creates the product catalog, the pricing rules, the supplier record and
one `OWNER` admin user. Then it prints this, which you should take literally:

> **The seed creates NO redeem codes.** Products with zero inventory cannot be
> sold. Import real inventory through `/admin/inventory` (CSV upload). Codes are
> AES-256-GCM encrypted on the way in and fingerprinted for duplicate detection.

Two things follow from that, and both are deliberate:

- **Every product is unbuyable until you import inventory.** That is correct.
  Seeding fake codes would mean selling customers codes that do not exist.
- **The supplier costs in `prisma/seed.ts` are PLACEHOLDERS** (e.g. `700` minor
  units for the $10 SKU). Replace every one with your real contracted pricing
  before you enable checkout. A placeholder that *understates* your cost publishes
  products at a margin you do not actually have, and the admin dashboard will
  report that fictitious margin back to you as if it were real.

The seed needs the **same `ENCRYPTION_KEY`** the app will run with. It only uses
it to prove the key is well-formed, but a mismatch at this stage means you will
find out during your first real inventory import instead.

Finally, delete `ADMIN_BOOTSTRAP_PASSWORD` from Vercel. The seed has already run.

### 4c. Inventory legality

Codes must come from an **authorised reseller or supplier contract**. Codes from
scraping, leaked voucher dumps or abused consumer accounts are stolen property:
reselling them is fraud, is chargeback-prone at ~$15 per dispute, and is a
criminal offence in most jurisdictions. The risk engine and the reconciliation
layer will not stop you. This is a legal constraint, not a technical one.

## 5. Register the Whop webhook

The webhook is the only path by which a payment becomes "verified". If it is not
registered, customers can pay and nothing will ever be delivered.

### 5a. Create the webhook

Whop dashboard → Developers → Webhooks → Create. Set:

```
URL:   https://yourdomain.com/api/payments/webhook
```
```
(Use your real production domain, not a .vercel.app preview URL.)
```

Whop shows the signing secret **exactly once**. Copy it immediately into
`WHOP_WEBHOOK_SECRET` on the Vercel project and redeploy. There is no way to
retrieve it later.

### 5b. Subscribe to these seven events

```
payment.succeeded
payment.failed
payment.pending
payment.canceled
refund.created
dispute.created
dispute_alert.created
```

Also subscribe to these two if the dashboard offers them — they carry the
*transitions* of the events above, not new information, but they keep refund and
dispute status current instead of leaving it stale until the next daily reconcile:

```
refund.updated
dispute.updated
```

### ⚠ `payment.refunded` and `payment.chargeback` DO NOT EXIST

This is the single most expensive mistake available in this integration, so it is
worth being blunt:

- There is **no `payment.refunded`** in Whop's API. Refunds are `refund.created`
  and `refund.updated`.
- There is **no `payment.chargeback`**. Chargebacks are `dispute.created` and
  `dispute.updated`. The pre-chargeback early warning is
  `dispute_alert.created`.

A mapping or subscription built on `payment.refunded` / `payment.chargeback`
fails **silently**. There is no error, no failed delivery, no alert. It simply
never arrives — and the dashboard will happily accept the event name and show you
a healthy, zero-delivery subscription.

The consequences for this business model specifically:

- You never learn about a refund → you keep selling a product whose cost you have
  already been reimbursed for.
- You never learn about a chargeback → you re-sell inventory that was reversed,
  so the same code goes to a second customer and the first one's claim wins.
- At a $3 SKU, Whop's processing fee alone is ~18% of revenue. The **~$15
  dispute fee** is a multiple of the order value. One chargeback can erase the
  margin on every order behind it.

`src/payments/whop/events.ts` and `src/payments/registry.ts` both document this
and both handle the real event names. The risk is purely in the dashboard
configuration.

### 5c. Confirm delivery

Whop sends a test event on creation if you ask it to. Check Vercel
**Runtime Logs** for a hit on `/api/payments/webhook` with a `200`.

To test by hand without a real payment, send a request with a deliberately wrong
secret and confirm you get `401` with code `INVALID_SIGNATURE` — that proves the
route is live, the secret is wired, and verification is genuinely enforced:

```bash
curl -i -X POST https://yourdomain.com/api/payments/webhook \
  -H 'Content-Type: application/json' \
  -H 'webhook-id: msg_test' \
  -H 'webhook-timestamp: '"$(date +%s)" \
  -H 'webhook-signature: v1,deadbeef' \
  -d '{"type":"payment.succeeded","data":{}}'
```

Expect `401`. A `200` here would mean the signature check is not running — stop
and fix that before going further.

## 6. Configure the Inngest app

Inngest is not optional decoration. Vercel has no long-lived workers, so
fulfillment steps must survive a cold start and a crashed process. Without
Inngest configured, the webhook enqueues nothing and **no code is ever delivered**,
while `/api/health` tells you so honestly rather than pretending.

**⚠ ORDER MATTERS:** do this *after* the first successful deploy, because Inngest
verifies the endpoint by calling it.

1. <https://app.inngest.com> → create an app if you have not.
2. Set the app's **Serve URL** (a.k.a. endpoint / target):

   ```
   https://yourdomain.com/api/inngest
   ```

   Not `https://api.inngest.com`, not your `.vercel.app` preview. The production
   domain, exactly.
3. Inngest generates an **Event Key** and a **Signing Key**. Put both into the
   Vercel project as `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY`, then redeploy.
4. Open the Inngest dashboard and wait for the app to sync. It calls your
   endpoint and lists the registered functions. An empty list means the app URL
   is wrong or the deploy predates the environment variables.
5. Send a test event from Inngest ("Events → Run Event") and confirm a function
   executes.

**Leave `INNGEST_BASE_URL` unset in Vercel.** Setting it points the client at a
dev server and fulfillment stops without an error.

## 7. First deploy and the verification checklist

Deploy:

```bash
vercel --prod
```

or push to the branch wired to Production. Watch the build log for the `prisma
generate && next build` step from `package.json`.

> **A successful build is not a running app.** `assertProductionConfig()` runs at
> *boot*, in production only. If it throws, Vercel reports a green deploy and
> every single request returns 500. Always finish with step 7.1.

### 7.1 `/api/health` — the honest integration report

```bash
curl -s https://yourdomain.com/api/health | jq
```

This is the authoritative answer to "is anything actually wired up". It reports
`REAL` / `SANDBOX` / `NOT_CONFIGURED` per integration and **never** prints a
secret value. This is exactly what you should see on a correct sandbox deploy:

```json
{
  "status": "ok",
  "integrations": {
    "payments": "SANDBOX",
    "email": "REAL",
    "redis": "REAL",
    "queue": "REAL",
    "encryption": "REAL",
    "paymentMethods": ["CARD"]
  },
  "notConfigured": [],
  "database": { "ok": true },
  "queue": { "ok": true, "depth": 0 }
}
```

Read it precisely:

| `payments` | Means |
|---|---|
| `SANDBOX` | `WHOP_ENVIRONMENT=sandbox` and the three Whop variables are set. **Correct for this deploy.** |
| `REAL` | `WHOP_ENVIRONMENT=production`. Do not expect this yet. |
| `NOT_CONFIGURED` | `WHOP_API_KEY`, `WHOP_WEBHOOK_SECRET` or `WHOP_ACCOUNT_ID` is missing. |

Anything in the `notConfigured` array means that integration is **off**, not
broken and not mocked. `payments` off means checkout returns
`503 PAYMENT_NOT_CONFIGURED`. `queue` off means nothing is ever delivered.

`status` is `ok` when the database is reachable and nothing is missing,
`degraded` when something is missing (**still HTTP 200** — restarting the process
would not fix a missing environment variable), and `down` with **HTTP 503** only
when the database is genuinely unreachable.

> `?verbose=1` is **ignored in production** by design. Verbose mode exposes
> alert state, worker holders and process ids; it is for local debugging only.
> Do not add an exception for it.

### 7.2 Confirm the cron secret is live

```bash
curl -i https://yourdomain.com/api/cron/reconcile
# expect: 404 Not Found        (CRON_SECRET unset → the route does not exist)

curl -i -H "Authorization: Bearer $CRON_SECRET" https://yourdomain.com/api/cron/reconcile
# expect: 200 {"ok":true,"durationMs":...}
```

A `401` on the second call means `CRON_SECRET` is set but mismatched.

### 7.3 Buy the $3 product with the Whop sandbox card

The end-to-end test that actually proves the system works.

1. Go to `https://yourdomain.com`, pick the `$1 Digital Redeem Code` product.
2. Enter your own email and click through to the hosted Whop checkout.
3. On the **sandbox** payment page, enter:

   ```
   Card number:  4242 4242 4242 4242
   Expiry:       any future date, e.g. 12/34
   CVC:           any 3 digits, e.g. 123
   ```

   The Whop sandbox is Stripe-backed, so the standard Stripe test card applies.
   If your sandbox declines it, use whatever test card the Whop sandbox dashboard
   documents — the application does not care which card is used, because the card
   is collected on Whop's hosted page and we only ever receive an opaque payment
   id back.
4. Complete the payment. You are redirected to the store's status page.

**Watch it reach `COMPLETED`:**

- Open the status page. It polls `GET /api/payments/status?reference=…&email=…`.
  The order should move `PAYMENT_PENDING → PAYMENT_VERIFIED → ALLOCATING →
  COMPLETED` over a few seconds.
- The **order reference** is shown on the status page and in your inbox. Keep it.
- Watch the Vercel Runtime Logs while this happens. You should see exactly one
  `POST /api/payments/webhook` with a `200`, and the Inngest dashboard should
  show one function execution per fulfillment step.

**Failures and what they mean:**

| Symptom | Meaning |
|---|---|
| Status stuck at `PAYMENT_PENDING`, webhook never arrived | §5 — the webhook is not registered against the production URL. |
| Webhook arrived with `401` / `INVALID_SIGNATURE` | `WHOP_WEBHOOK_SECRET` is wrong, or you set the *production* secret while on sandbox. They are different values. |
| Webhook arrived, status still `PENDING`, log shows `REPLAY_DETECTED` | Timestamp outside the 300s window, or the same `providerEventId` was already processed. Expected on redelivery; not a bug. |
| Webhook arrived, order went to `MANUAL_REVIEW` | Amount or currency did not match the order snapshot. **This is the system working.** Do not "fix" it by bypassing the check — read the reconciliation record. |
| Webhook arrived, status `PAYMENT_VERIFIED`, then nothing | Fulfillment was never enqueued: `queue` is `NOT_CONFIGURED`. §6. |
| `FULFILLMENT_FAILED` with an email error | `EMAIL_SEND_FAILED`. Check the provider's bounce/domain-verification state. |

### 7.4 Confirm the code arrives by email and is NOT in the browser

This is the security property the whole delivery design exists for, so check it
explicitly rather than assuming it.

1. **The email arrives** with the redeem code in the body, to the address you
   entered at checkout. Confirm it within a minute or two. Also confirm it is not
   in spam — SES needs a verified domain and a warm-up path; Resend is simpler
   for a first send. A code in spam is an unredeemable paid order.

2. **The code is NOT in the browser.** Verify all three:

   - `GET /api/payments/status` returns order state and delivery status. It has no
     field containing the code, by design. Fetch it directly:
     ```bash
     curl -s "https://yourdomain.com/api/payments/status?reference=ORD-XXXX&email=you@example.com" | jq
     ```
     Confirm there is no code anywhere in the payload.
   - View-source the status page and search for the code. It is not there.
   - Check the order detail page in `/admin`. **The admin can see the code** —
     that is an operator capability, not a leak. It is still never logged, never
     emailed to anyone else, and never returned by a public API.

   Delivery is by email only. That is not a convenience; rendering the code in the
   browser would put it in history, on a shared machine and in any screen
   recording the customer made.

3. **Status-page enumeration is closed.** Re-request the same reference with a
   *different* email and confirm you get an identical `found: false` response,
   not an error that distinguishes "exists but wrong email" from "does not exist".

### 7.5 Metrics

```bash
curl -s -H "Authorization: Bearer $METRICS_TOKEN" https://yourdomain.com/api/metrics | head -40
```

Without `METRICS_TOKEN` this endpoint does not exist. There is no unauthenticated
mode and no query-string fallback, deliberately.

## 8. Going to production

Do not skip §7. Every step below assumes a working sandbox deployment.

### 8.1 Create the live Whop company

Create a **live** company in the Whop dashboard (separate from sandbox), issue a
live API key with the same five scopes, and note the live account id (`biz_…`).

### 8.2 Register the production webhook and swap the secret

Create the webhook against `https://yourdomain.com/api/payments/webhook` in the
**live** company and subscribe to the same events from §5b.

Then, on the Vercel project, replace **three** variables at once:

```
WHOP_ENVIRONMENT     = production
WHOP_API_KEY         = <live key>
WHOP_WEBHOOK_SECRET  = <the NEW secret from the LIVE company>
```

> ⚠ The sandbox and production webhook secrets are **different values**. Setting
> `WHOP_ENVIRONMENT=production` while leaving the sandbox secret in place is the
> most common production mistake here: the deploy goes green, `/api/health` says
> `REAL`, and **every** webhook is rejected with `INVALID_SIGNATURE`. No payment
> is ever verified, and customers pay for nothing.

`WHOP_ACCOUNT_ID` must also be the live account. Redeploy after changing these —
they are read at request time, but the deploy also guarantees the values are not
sitting half-applied.

### 8.3 Re-run the verification checklist

**Not just `/api/health` this time — the full §7.3 path**, using the live
company's hosted checkout with a real card at the real $3 price. Then confirm:

```bash
curl -s https://yourdomain.com/api/health | jq '.integrations.payments'
# "REAL"   ← must now be REAL, not SANDBOX
```

Then check the admin dashboard reports **net** margin (from
`Payment.netAmountMinor`, after Whop's 2.7% + $0.30) rather than gross. At a $3
price the fixed fee component dominates; if net margin is negative, your supplier
costs are still the §4 placeholders. **Fix that before you take more orders.**

### 8.4 Enable admin MFA

⚠ There is no MFA UI page in this repository. `/admin/account` does not exist
despite what the seed output suggests. Enrolment is reachable only via
`POST /api/auth/mfa/enrol`, which needs an authenticated session, a CSRF token and
a password re-check.

The reliable sequence, run from the **browser console** while logged in at
`https://yourdomain.com/admin`:

```js
const csrf = document.cookie.match(/rdm_csrf=([^;]+)/)?.[1];
const post = (body) => fetch('/api/auth/mfa/enrol', {
  method: 'POST',
  headers: { 'content-type': 'application/json', 'x-csrf-token': csrf },
  body: JSON.stringify(body),
}).then(r => r.json()).then(console.log);

// 1. START — re-check the password. Returns the otpauth:// URI ONCE.
await post({ action: 'start', password: 'YOUR_ADMIN_PASSWORD' });

// 2. Add the secret to your authenticator app (Google Authenticator, 1Password,
//    Authy…). The `uri` above is an otpauth:// string; paste the base32 secret
//    into the app if it will not scan a QR code.

// 3. CONFIRM — prove the app holds the same secret. 6 digits, 30s period.
await post({ action: 'confirm', code: '123456' });
```

`confirm` also returns your **recovery codes, once**. Store them now; they are
stored only as bcrypt hashes and cannot be retrieved again.

`start` deliberately does **not** enable MFA — only `confirm` does. That is
intentional: enabling on `start` would let anyone with a stolen session cookie
lock *you* out of your own account by enrolling their own authenticator.

If you have no `rdm_csrf` cookie, reload `/admin` once so the app can mint it.

## 9. Scaling notes

### 9.1 What is per-instance, what is shared

This is the mental model that matters most when something breaks under load.

**Shared — correct across every instance:**

| State | Where |
|---|---|
| Orders, inventory, payments, events, audit | Postgres |
| Rate limits, idempotency keys, queue gauges, worker leases | Upstash Redis |
| Fulfillment workflow state and retries | Inngest |
| Encrypted redeem-code inventory | Postgres (AES-256-GCM at rest) |

**Per-instance — resets on every cold start and is not shared:**

| State | Consequence under traffic |
|---|---|
| In-memory rate-limit fallback (**only** when Redis is unset) | The effective limit is `limit × instance count`. With Redis down you are effectively unprotected. |
| Prometheus metric registry | `/api/metrics` on instance A does not contain the counters from instance B. A scrape sees one instance. Percentiles derived from histograms are biased by whichever instance the scraper hit. |
| Inngest function registration | Rebuilt on every boot. Harmless — `/api/inngest` is the route that serves traffic. |
| Process uptime, PID | Cosmetic. |
| Node module cache / warm start | Vercel reuses warm instances under load and recycles idle ones. |

**The practical consequence:** the correctness guarantees do **not** depend on
instance count. Oversell protection is a unique index plus
`SELECT … FOR UPDATE SKIP LOCKED`; duplicate-webhook protection is a unique index
on `PaymentEvent.providerEventId`; state transitions go through a transition
table. Twenty instances and twenty processes enforce them identically. This is
the property that lets you scale out without a distributed-systems redesign.

### 9.2 Connection exhaustion — the real serverless Postgres failure

A Vercel Function is short-lived and horizontally scaled, and **every warm
instance holds a database connection for its whole lifetime**. The failure mode
under card traffic is not "the database is slow" — it is "the server ran out of
connection slots", surfacing as `too many clients already` or Prisma `P1001`.

```
safe concurrent functions ≈ (max_connections − headroom) / connection_limit
```

With `max_connections = 50` and `connection_limit = 5`, roughly 8 concurrent
functions are safe. With `connection_limit = 20` and the same budget, you have
already lost.

Start at `connection_limit=5&pool_timeout=15`, then tune from observed errors —
not from theory. If you see `P1001`, **lower `connection_limit`** before you
upgrade the database; instance count is Vercel's to scale, and your ceiling is
the product of the two.

Put the database in **us-east-1** to match `regions: ["iad1"]`. A transatlantic
round trip on every query adds latency to checkout, status polling and the
fulfillment path simultaneously.

### 9.3 Function timeouts — why `vercel.json` is shaped the way it is

A stuck request occupies a function instance for its entire `maxDuration`. With
short durations, a pathological request releases its instance quickly instead of
pinning one and starving concurrent traffic. That is why almost everything in
`vercel.json` is 5–15 seconds.

The deliberate exceptions:

| Route | `maxDuration` | Why it needs longer |
|---|---|---|
| `/api/cron/reconcile` | 300 | Pages through the provider API and compares every order in a 72-hour window. This is genuinely minutes of work. |
| `/api/cron/fulfillment-recovery` | 120 | Re-runs stalled fulfillment jobs; each one does a full allocation and an email send. |
| `/api/inngest` | 120 | Inngest executes fulfillment steps synchronously through this endpoint. It needs headroom for a DB allocation plus an outbound provider call under load, but not minutes — each retry is a *separate* invocation. |
| `/api/cron/inventory-reaper` | 60 | One conditional bulk update. |

Everything else is capped at 15s or below, including the webhook at 10s: Whop
expects a 2xx in under 5 seconds and disables a webhook after 24 hours of
failures. The webhook acknowledges fast and hands the real work to Inngest.

Route-level `export const maxDuration` in the source is authoritative where it
exists; `vercel.json` covers the routes that declare none. Keep the two in sync
if you change one.

### 9.4 What to watch

The metrics that matter, all exported from `/api/metrics`:

| Signal | Metric | Watch for |
|---|---|---|
| **Queue depth** | `queue_depth`, `queue_oldest_job_age_seconds` | Depth climbing, or the oldest job older than 15 minutes. `FULFILLMENT_LATENCY` is the customer-visible number: paid order → code delivered. |
| **Provider error rate** | `provider_error_rate{provider}` | > 0.5 over a window with ≥ 5 samples. `payment_success_rate` below 0.8 is the same story from the money's side. |
| **Webhook health** | `webhook_verification_failures_total{reason}` | Any sustained non-zero. A rising `reason="signature"` after a secret swap means a stale secret. |
| **Database** | `database_up`, `database_probe_latency_ms` | `database_up == 0` is a total outage of the payment path. Latency climbing toward the pool timeout is exhaustion beginning. |
| **Fulfillment** | `fulfillment_total{status}`, `email_latency_ms` | Failures or climbing email latency point at the email provider, not at your code. |
| **Reconciliation** | `reconciliation_mismatches_total{type}` | **Any** increase is a real discrepancy between your records and the provider. Read the reconciliation rows; do not dismiss it. |
| **Inventory** | `inventory_levels{product}`, `inventory_depleted_total` | `inventory_depleted` means customers hit "out of stock" and left. |
| **Alerts** | `alerts_fired_total{code,severity}` | Codes: `PAYMENT_PROVIDER_UNAVAILABLE`, `WEBHOOK_VERIFICATION_FAILURE_SPIKE`, `FULFILLMENT_FAILURE_SPIKE`, `INVENTORY_DEPLETED`, `QUEUE_BACKLOG`, `RECONCILIATION_MISMATCH`, `ABNORMAL_PAYMENT_ACTIVITY`. |

### 9.5 Where the dashboards are

| What | Where |
|---|---|
| Function invocations, errors, duration, cold starts | Vercel dashboard → your project → **Observability** tab, or `vercel logs <url> --follow` |
| Build logs | Vercel → **Deployments** → select a build → **Build Logs** |
| Crons: did they fire, what did they return | Vercel → **Settings → Crons**. Also each cron response is JSON with `ok` and `durationMs`. |
| Workflow runs, step retries, dead letters | <https://app.inngest.com> → your app |
| Webhook deliveries, failures, the subscription list | Whop dashboard → Developers → Webhooks |
| Payments, disputes, refunds | Whop dashboard |
| Order/inventory/refund detail | The app's own `/admin` |
| PromQL | `/api/metrics`, behind `METRICS_TOKEN` |

**Wire a real alert before you need it.** `/api/metrics` is a Prometheus endpoint
and nothing scrapes it by default. A `PAYMENT_PROVIDER_UNAVAILABLE` alert at
3am is the difference between a bad morning and a bad week.

### 9.6 If traffic actually spikes

1. Confirm the database is the bottleneck, not the code, before changing
   anything — check `database_probe_latency_ms` against your provider's own
   dashboard.
2. Lower `connection_limit` and/or raise the database's `max_connections`.
3. Consider Vercel **Fluid compute** (a project setting) for more concurrency per
   instance. Check current availability and cost against your plan first.
4. Verify your **Inngest plan's concurrency limit** — this is usually the real
   ceiling on fulfillment throughput, because fulfillment is serialized through
   the queue by design.
5. Do **not** "fix" a backlog by increasing fulfillment concurrency blindly. Every
   concurrent fulfillment run competes for the same inventory rows and the same
   email provider quota. A backlog that drains slowly is safer than one you
   trigger a duplicate-send incident to clear.

## 10. Troubleshooting

| Symptom | Likely cause | What to do |
|---|---|---|
| Deploy is green; every request 500s | `assertProductionConfig()` threw at boot — a required variable is missing | Read the **Runtime Logs** error: it names the missing variables. Set them and redeploy. |
| `/api/health` → `503`, `status: "down"` | Database unreachable | Check `DATABASE_URL`. Most often a missing `sslmode=require` on a remote host. |
| `/api/health` → `degraded`, an integration in `notConfigured` | That integration's env vars are absent | Set them. **Degraded is a report, not a fault** — the process is serving. |
| `/api/metrics` returns 404 | `METRICS_TOKEN` unset | That is the design. Set it, then resend with `Authorization: Bearer …`. |
| `/api/cron/*` returns 404 | `CRON_SECRET` unset → the route is disabled on purpose | Set it, redeploy, retest with the bearer header. |
| `/api/cron/*` returns 401 | `CRON_SECRET` set but the request's token does not match | Confirm you are using the Production value, and that you are not hitting a Preview deployment. |
| Crons never fire at all | Hobby plan frequency limits, or the project is not on a production deployment | Check the plan (§1) and confirm crons are configured on the **production** deployment, not a branch preview. |
| Webhook returns 401 `INVALID_SIGNATURE` in production | Sandbox `WHOP_WEBHOOK_SECRET` still set while `WHOP_ENVIRONMENT=production` | §8.2. Create the webhook on the live company and copy **that** secret. |
| Webhook returns 400 on every delivery | Signature computed over re-serialised JSON | The signature is over the **exact received bytes**. If you are testing with a hand-built request, you cannot reproduce it; test through the Whop dashboard. |
| Webhook returns 400 `REPLAY_DETECTED` | Timestamp outside the 300s window, or a duplicate `providerEventId` | Expected on redelivery. If it is every delivery, check `WEBHOOK_TOLERANCE_SECONDS` and the sender's clock. |
| Webhook 200 but the order never advances | Amount/currency mismatch → order is in `MANUAL_REVIEW` | Look at the reconciliation record. **Do not bypass the check.** |
| Paid, but no email ever arrives | Fulfillment never enqueued | Check `queue` on `/api/health`. If `NOT_CONFIGURED`, §6. Then check the Inngest dashboard for a failed run. |
| Email send fails, order stuck `FULFILLMENT_PENDING` | `EMAIL_SEND_FAILED` | Provider-side: unverified domain, unverified `EMAIL_FROM`, sandbox-mode SES, or rate limit. The 5-minute recovery cron will re-run it once fixed. |
| `P1001` / `too many clients already` | Database connection exhaustion | §9.2. Lower `connection_limit`; confirm you are on a pooled URL. |
| Prisma errors at deploy time but not locally | `prisma generate` did not run, or the binary does not match the deploy platform | Confirm the build log contains `prisma generate`. Node engine must be ≥ 20.11. |
| `pnpm db:deploy` "succeeds" and no tables exist | **No `prisma/migrations/` directory exists** | §4a, Option A. This is a known gap in this repository. |
| The code appears in the browser / in a log / in an API response | A real bug — this must never happen | Grep for the code, find the path, and treat it as a P0. Delivery is email-only by design. |
| `payment.refunded` / `payment.chargeback` never arrives | **They do not exist in Whop's API** | §5b. Use `refund.created` / `dispute.created` / `dispute_alert.created`. |
| MFA enrolment page `/admin/account` is 404 | **The page does not exist in this repository** | §8.4 — use the browser-console sequence against `/api/auth/mfa/enrol`. |
| Requests are slow only in production | Database is in a different region from `iad1`, or an unpinned Whop API version | Move Postgres to us-east-1 (§9.2). Confirm `WHOP_API_VERSION_DATE` is still set. |
| Reconciliation reports mismatches daily | Local records and the provider disagree | Real. Investigate the reconciliation rows before anything else — this is the safety net for missed webhooks, and it is telling you it caught something. |
